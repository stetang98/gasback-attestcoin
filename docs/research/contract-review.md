# GasBack contract review

Reviewed on 2026-09-12 against commit `eb31caa240ff156df3c0e1dd06643533e99d92c0`.

Scope: `chain/contracts/`, the 42 cases generated by `chain/test/gasback.test.cjs`, the test harness, compiler settings and exported deployment artifacts, compared with `docs/superpowers/specs/2026-09-12-gasback-design.md` and the implementation plan. This was an independent source review, not a professional audit or a claim of live deployment success. No contract or test source was changed.

## Findings

No actionable P0, P1 or P2 defect was identified in the reviewed contract scope. This conclusion is conditional on the Creditcoin native verifier correctly authenticating the transaction payload and the Sepolia chain-key mapping. Those are external integration assumptions, not implemented by the unit-test harness.

## Limits and required integration evidence

- The local `VerifierHarness` is an exact-tuple allowlist installed at the precompile address. It does not verify Merkle inclusion or continuity. Its synthetic source signatures and contract-recipient fixtures exercise application policy only. The README already states this accurately. Native proof verification and a real target payout remain separate acceptance gates.
- Before declaring the project ready, retain an observed testnet run with sponsor ticket issuance before the eligible source action, authentic failed receipt, native proof, successful target receipt/event, consumed state and beneficiary payment. Also retain native tampering/success rejection and duplicate-claim rejection. The initial source failure produced before ticket issuance must remain labeled as a diagnostic integration fixture.
- Prospective authorization is sponsor policy: the contract cannot prove that the source transaction happened after ticket issuance from an unproven source UTC timestamp. The source block range must be chosen appropriately. This is explicitly documented in the design and `chain/README.md`.
- Deliberate reverts are possible, gas limit is not gas used, rebates are fixed subsidies, tickets do not reserve funds, and excess unclaimed funds have no withdrawal path. These are declared MVP constraints, not newly discovered defects. They must remain visible in the submission claims.
- Most rejection tests assert any revert rather than a specific custom error. This is acceptable for the current state-safety assertions but does not by itself prove which rejection branch ran. Error-specific assertions would be useful if future changes make failure diagnosis ambiguous; no extra test run or implementation change was required by this review.
